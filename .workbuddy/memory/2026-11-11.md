## 敌人发射器接入 Repeater 弹幕调度

**背景**：`emitter_enemy` 的 162 个 attack 函数全靠 `attack_time` 手写 `= N` / `mod N` 判断，
触发逻辑无法复用，关键帧还会漏。

**方案**：Repeater 增加 `owner` 锚定，时间轴挂到发射器自身的 `rep_frame` 上。

### 改动
- `scripts/Repeater/Repeater.gml`
  - `Repeater_Create` 新增第 6 参 `_owner`（可选）
  - Step 中 owner 锚定：owner 不存在 → done；owner 的 `rep_frame` 未推进 → 整帧跳过（timer/index 保留，可恢复）
  - 新增 `Repeater_CancelList(ids)` 批量取消
  - **修复**：`_condition` 默认值由 `function(){}` 改为 `undefined`。
    原默认空函数返回 undefined，`!undefined` 为真，会被判成条件不满足而立即终止。
- `objects/emitter_enemy/Create_0.gml`
  - 新增 `rep_frame`（Step 驱动）、`_atk_reps`
  - 新增 API：`Fire` / `FireStop` / `At` / `Every` / `During`
  - `end_attack()` 开头加 `FireStop()`
- `objects/emitter_enemy/Step_0.gml`
  - `if(!enabled) exit` 之后 `rep_frame++`
  - 新增兜底：`current_attack == undefined && _atk_reps 非空` 时 `FireStop()`
- `objects/emitter_enemy/CleanUp_0.gml`（新增，eventType 12）
  - 实例销毁 / 切换房间时 `FireStop()`
- `objects/emitter_enemy/emitter_enemy.yy` 注册 CleanUp 事件

### 语义
- 冻结（`instance_deactivate_all`）：world 与 emitter 一起停 → Repeater_Step 不跑 → 暂停
- `enabled = false`：`rep_frame` 不增长 → 暂停，恢复后从原进度继续
- 敌人死亡 / 切房间：实例销毁 → `instance_exists` 失败 + CleanUp → 作废

### 验证
Python 复刻调度算法模拟：
- `During(4,39,4)` 触发帧 = 4,8,...,36 共 9 次，与原 `attack_time mod 4` 逻辑一致
- 中间冻结 20 帧，恢复后仍发满 9 次
- 第 20 帧销毁后停止发射

### 注意
- `At()` / `During()` 必须在 `attack_time = 1` 处集中注册，否则延迟算错
- 触发时机与原 `attack_time` 判断存在 ±1 帧差异（Step 执行顺序导致），视觉无感

## During 的 end 语义改为左闭右开（修正"多发一帧"）

原来的 `_count = floor((_end-_start)/_iv) + 1` 是**闭区间**上界：
当 `(end-start)` 正好被 `interval` 整除时，会在 end 那一帧多发一次。
`During(6, 300, 6)` → 50 发（含 300），而原逻辑 `attack_time < 300` 只有 49 发。

改为 `_count = ceil((_end-_start)/_iv)`，即 `[start, end)`：

| 调用 | 旧 | 新 | 对应原条件 |
|---|---|---|---|
| og0b `During(4,39,4)` | 9 发 4..36 | 9 发 4..36 | 不变 |
| og0b `During(3,44,3)` | 14 发 3..42 | 14 发 3..42 | 不变 |
| xeno `During(1,100,10)` | 10 发 1..91 | 10 发 1..91 | 不变 |
| xeno `During(6,300,6)` | 50 发 6..300 | 49 发 6..294 | 与原 `<300` 一致 |
| xeno `During(10,300,10)` | 30 发 | 29 发 10..290 | 与原 `<300` 一致 |
| xeno `During(3,300,3)` | 100 发 | 99 发 3..297 | 与原 `<300` 一致 |

**不整除时新旧结果相同**，只有整除（如 end 恰好落在帧序列上）才有差别。
以后写 `During(a, b, i)` 直接读作 `a <= t < b`。

## RepTick 改为正向遍历（修复同帧顺序颠倒）

**现象**：曲线追踪弹某些批次飞到一半目标坐标突变。

**根因**：`RepTick` 原先为 `array_delete` 方便用了**反向遍历**，
同一帧内多个节点的执行顺序因此被颠倒。xenomorph attack_1 里
B1（刷新 tx/ty）先注册、B2（发射曲线弹）后注册，原代码顺序是"先刷新再发射"，
反向遍历却让 B2 先跑。两者只在 `mod 40 = 0 && mod 3 = 0` 的帧冲突 ——
即第 120、240 帧，正好是"某些批次"。

**修复**：改正向遍历。用固定 `_n = array_length(_reps)` 限定本次处理范围，
保证本帧回调中新注册的节点留到下一帧（不会同帧多推进一次），
删除时同步 `_n -= 1`。

**验证**：模拟两节点在第 120 帧冲突
- 反向遍历：曲线弹读到 tx = 0（旧值）
- 正向遍历：读到 tx = 2（新值）✓

**结论**：调度器遍历方向必须与书写顺序一致，否则"先在回调里改状态、后在另一个回调里读"的写法会静默失效。

同期还给 B2 的 `custom_function` 加了 `method(id, ...)` 绑定（防匿名函数 self 落到发射器）。
